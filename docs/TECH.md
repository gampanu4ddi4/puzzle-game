## 2. 설계와 구현의 우선순위

[GDD](GDD.md)의 문법과 각 레벨의 상태표가 요구사항입니다. 아래 이름·경로는 **향후 제안**이며 존재하는 파일 목록이 아닙니다. 이번 작업에서 클래스나 공개 API를 추가하지 않습니다.

```text
PuzzleRoomV2 ── 장치 입력 ──> 상태 변경 요청
     │                          │
     │                   점유·범위·연결 검사
     │                          ↓
     ├─ 힌트/관찰 이벤트 ← 안정 상태 갱신 → 화면·충돌·소리
     └─ 저장 스냅샷 ←─────────────┘
```

입력은 먼저 의미 있는 요청으로 바꾼 뒤 한 번에 상태를 확정합니다. 렌더링 프레임마다 시선을 떼었는지로 퍼즐 상태를 순환하지 않습니다. 효과음·모니터 표시·실제 충돌·저장 상태는 같은 확정 결과를 사용합니다.

## 3. 최소 시스템 계약

### 3.1 상황 관리자

향후 `PuzzleRoomV2`는 ID, 진입 안전 지점, 현재 안정 상태, 장치 목록, 완료 조건, 힌트 진전 이벤트, 연출 재생 기록을 소유합니다.

제안 인터페이스:

| 요청 | 의미 |
|---|---|
| `request_action(device_id, action)` | 해당 방에서 허용한 장치 입력만 수신 |
| `snapshot_state()` | 안정된 논리 상태를 반환, 노드 경로 대신 상태 ID 사용 |
| `restore_state(data)` | 재생 효과 없이 상태·충돌·표시를 함께 복구 |
| `reset_current()` | 현재 방 초기값·안전 위치 복구, 이전 완료 유지 |
| `is_complete()` | 실제 요구 상태와 통과 조건 검사, 입력 순서 문자열 비교 안 함 |
| `report_evidence(evidence_id)` | 새로운 증거 확인, 반복 입력과 구분 |

실제 GDScript 시그니처·소스 분할은 구현 시 엔진과 기존 구조에 맞춰 결정하되 위 동작을 바꾸지 않습니다. 외부 서비스·네트워크·LLM은 필요 없습니다.

### 3.2 J: 공유 상태와 접속

`SharedStateOwner` 하나에 여러 표현을 연결합니다. P01·P02·P09에서 어느 표현으로 입력해도 실제 소유자 한 번만 갱신합니다. 표현별로 별도 값을 저장해 어긋나는 구조를 피합니다. 같은 효과음을 두 표현에서 재생할 때 합산 음량을 보정합니다.

`Connection`은 고유 ID, 두 끝, 현재 노선, 허용 전달 종류(몸/빛/케이블/부력대)를 가집니다. 방향·전진/후진으로 노선을 결정하지 않습니다. 현재 LoopGate의 방향별 타깃은 v2 연결 의미와 다르므로 바로 복사하지 않습니다. 위치·방향·속도 대응 보존이라는 기존 기술만 재사용 후보입니다.

빛·케이블은 범용 물리 광선·로프를 포털마다 재귀 계산하지 않습니다. P03·P10의 미리 정의한 경유점 그래프를 사용합니다. 케이블 길이는 해당 경로의 명세 길이 합이며 월드 좌표상 직선거리가 아닙니다. 전원은 실제 연결 성립에서 계산합니다.

### 3.3 C: 설비·수위·운반

수위는 명령 완료 후의 안정된 높이 값과 시각 보간으로 표현합니다. P04는 동일 단면적 수조 둘이므로 연결 개방 시 두 높이의 평균, 급수·배수 시 명세의 HIGH/LOW를 계산합니다. 보간 도중 입력은 완료 뒤 적용해 미세 타이밍 해법을 만들지 않습니다. 연동·차단·급수·배수는 레벨 계약을 따르며 실제 유체 역학은 시뮬레이션하지 않습니다. 물 표현·부력교·수압 걸쇠·눈금은 같은 확정 수위를 참조합니다.

P05의 시험 펄스는 결과 증거를 남기는 짧은 입력이며 본 배수와 다릅니다. 별도 `evidence_peak` 표시를 남겨 청각·반응 속도에 의존하지 않게 합니다. 청음구 소리는 방사 위치를, 유량·부표는 실제 원인 노선을 참조합니다.

P06 부력대는 2방향×3정지점의 유한 상태입니다. 운반 가능 여부는 개구부 폭·방향·점유 상태로 판정하고, 실패 시 이전 정지점으로 복귀할 수 있습니다. 데크 핸들과 수중 핸들은 같은 요청을 보냅니다. 머리 잠김 시간·타일 색으로 순간이동시키지 않습니다.

### 3.4 O: 정보 출처와 구조 유지

`Feed`는 live/archive를 명시하며 live는 실제 장치 상태와 연결합니다. P07 보관 화면은 미리 정한 이미지입니다. 실시간 영상이 조작과 무관하게 과거 화면으로 바뀌는 오류 연출은 없습니다. 반사 경유 영상은 실제 좌우 대응과 그림이 같아야 합니다.

`StructureZone`은 구조 ID와 현재 형태를, `ObservationAnchor`는 선택된 실제 촬영 구역·REC·유지한 구조 상태를 가집니다. P08·P10의 선택지는 미리 정한 구역 집합으로 표현합니다. 플레이어 FOV·해상도·모니터를 바라보는지와 독립적입니다. 카메라 화면은 해당 실제 구역을 보여 주며 임의의 다른 범위를 유지하지 않습니다.

REC ON 시 현재 구역 상태를 잡습니다. 구조 변경 요청은 유지되지 않은 구역에만 적용합니다. REC OFF 시 보류 요청을 적용하되 점유 중이면 안전하게 지연합니다. 보류된 요청·유지 상태·실제 구조 상태는 따로 저장합니다. 카메라가 물 수위나 플레이어를 정지시키지는 않습니다.

### 3.5 출입 사건

P11의 사건은 실제 경계 통과 하나에 `event_id` 하나입니다. 공유 경계의 B/C 표현은 같은 사건 ID를 사용합니다. 그룹을 묶으면 `(group_id, event_id)` 단위로 한 번만 집계합니다. 다른 시각의 별개 통과까지 영구 제거하지 않습니다.

시험 레버는 별도 시뮬레이션 상태를 갱신하며 실제 입장 기록을 바꾸지 않습니다. 실제 퇴장 통과는 해당 방의 1회 처리 래치와 연동합니다. 정정 손잡이가 이 래치·입장 기록·안전 위치를 함께 복구합니다. P11 숫자를 건물 전체 생존자 수로 표시하지 않습니다.

### 버전과 호환성

향후 진행 저장은 `schema_version=2`, 캠페인 ID `saesol_v2`, 새 퍼즐 ID를 사용합니다. 기존 캠페인 ID를 v2로 조용히 해석하거나 옛 방 위치를 새 방으로 억지 변환하지 않습니다. v1 진행 파일이 실제 발견되면 원본을 보존하고 ‘기존 기획의 저장’이라고 표시한 뒤 v2 새 게임을 제공합니다. 현재 저장 파일의 존재·내용은 이번 작업에서 확인하거나 변경하지 않았습니다. 설정 파일은 호환되는 키만 유지합니다.

저장 슬롯 3개와 원자적 교체 방식은 향후 요구사항입니다. 현재 이미 구현됐다고 주장하지 않습니다. 전환 중 저장 요청은 다음 안정 상태까지 미루고, 안정 상태 전후 중 하나를 완전하게 기록합니다.

## 5. 가시성·전환·안전

- 개구부의 대응은 렌더링·충돌·케이블 경로에 같은 정의를 사용합니다. 눈으로 보이는 통로와 실제 목적지가 다르면 안 됩니다.
- 전환은 장치 요청에 대한 결과이며 숨기기 위해 플레이어가 돌아보기를 기다리지 않습니다. 필요한 위치를 고정 프레임·접합선으로 가립니다.
- 통과 면의 재진입 억제는 같은 프레임에 두 번 처리하지 않는 기술 조건입니다. 후진하면 정답이 되는 설계 조건이 아닙니다.
- 점유 보호는 패널 회전·수위 변경·문 복귀·구조 변경에 공통으로 적용합니다. 안전 지점·보류 표시·재요청 경로를 명세합니다.
- 저장 복구 시 점유와 실제 구조가 불일치하면 안정된 안전 지점으로 몸만 옮깁니다. 퍼즐 해법·장치 상태를 몰래 초기화하지 않습니다.
- 필수 영역의 가독성은 저품질·밝기 조절·소리 끄기·그레인 끄기에서도 유지해야 합니다.

## 6. 성능과 제작 경계

기존 Forward+와 현재 조명 자산을 그대로 둡니다. 새 장면의 조명 방식은 장치 전환과 함께 검토하되 이 문서 작업에서 프로젝트 렌더링 설정을 바꾸지 않습니다. 반복 메시·재질을 공유하고, 구조 구역은 사전 제작한 형태를 교체합니다. 동적 변형을 범용 건축 시뮬레이터로 만들지 않습니다.

P07 실시간 화면은 필요한 두 뷰만, P08·P10은 선택된 카메라 뷰만 갱신하는 방향입니다. 화면 품질을 낮춰도 판정과 화면의 정보가 달라져서는 안 됩니다. 수중 접속은 한 쌍의 전용 공간으로 제한합니다. 범용 재귀 포털·무한 거울·유체·물리 케이블은 제외합니다.

1080p 60 fps는 기존 제작 가정으로 남기되 이번에 성능을 측정하지 않았습니다. 실제 최소 사양·성능 예산·셰이더 선택은 대표 구간 구현 뒤 사용자 요청에 따른 측정으로 정합니다. 게임 실행·빌드·자동 테스트는 이번 문서 작업에서 수행하지 않습니다.
